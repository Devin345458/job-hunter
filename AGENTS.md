# AGENTS.md

## Project
- Name: `job-hunter`
- Purpose: Automated job discovery, AI matching, resume tailoring, and application tracking.
- Runtime: Nuxt SSR app with Nitro server routes and scheduled tasks.

## Tech Stack
- Nuxt `^4.3.1` + Vue `^3.5`
- Vuetify `^3.11` via `vuetify-nuxt-module`
- TypeScript (app + server)
- Drizzle ORM + `better-sqlite3`
- SQLite database (default: `./data/job-hunter.db`)
- PDF generation with `pdfmake`

## Key Directories
- `app/`: pages, layouts, components, composables, styles
- `server/api/`: Nitro API endpoints
- `server/tasks/`: scheduled job search + match tasks
- `server/utils/job-sources/`: pluggable job source adapters
- `server/db/`: schema, migrations, seed script
- `data/`: SQLite files

## Dev Commands
- Install: `npm install`
- Dev server: `npm run dev`
- Production build: `npm run build`
- Preview build: `npm run preview`
- Generate migrations: `npm run db:generate`
- Apply migrations: `npm run db:migrate`
- Seed data: `npm run db:seed`
- Drizzle Studio: `npm run db:studio`

## Implementation Conventions
- Prefer TypeScript-first changes with explicit types for API payloads and DB interactions.
- Preserve source adapter contract in `server/utils/job-sources/types.ts`.
- Keep deduplication behavior stable (`source + sourceId`).
- Keep AI behavior conservative: tailor existing experience, never fabricate claims.
- Use SCSS + BEM naming for custom styles.

## Nuxt + Vuetify Notes
- Vuetify config lives in `nuxt.config.ts`.
- Vuetify SASS settings live in `app/assets/scss/components.scss` (`moduleOptions.styles.configFile`). Every component's styles compile through it, so font and radius overrides go there. `global.scss` loads it first, then the full `vuetify` stylesheet.

## Pipeline architecture (added 2026-11-01)
- Login: `server/middleware/00.auth.ts` gates every page and `/api/*` route. Public: `/login`, `/api/auth/*`, `/api/health`, build assets, and the sandbox form (token-checked).
- Shared contract: `shared/types/pipeline.ts` defines every JSON column shape and the `ReviewItem` the dashboard reads. Change it first.
- Data model: migration `0001_pipeline_learning_demos` adds job enrichment and scoring columns, application pipeline columns, and the tables `decisions`, `learned_rules`, `demo_projects`, `pipeline_runs`, `score_history`, `sandbox_submissions`, `ai_calls`.
- Claude calls go through `aiStructured()` / `aiText()` in `server/utils/ai.ts`: structured outputs, model fallback, cost logging to `ai_calls`, daily budget (API key calls only). Each step runs on Devin's subscription or the API key; see Claude subscription backend.
- Prompt caching (added 2026-11-03): a prompt is built with `cachedPrompt(stable, varying)` (and `cachedSystem()` for a system prompt worth caching alone): instructions, then the knowledge base, then questions already asked, each ending at a cache breakpoint, and the per-job text last. Keep anything that changes per job or per call (a posting, a date, an id) out of the stable parts and keep their order deterministic (`loadKnowledge()` sorts by id; question lists order by id), or every call misses. Prefixes under 512 tokens (4096 on claude-haiku-4-5) never cache. `ai_calls.cache_read_tokens` and `cache_write_tokens` (migration 0007) show hits; `usageCost()` in `server/utils/model.ts` prices them.
- Tasks: `pipeline:daily` (every 3 hours, 06:00 to 21:00 America/Chicago; `PIPELINE_CRON` in shared/utils/schedule.ts) runs the `DAILY_STEPS` in order (`repos:index`, `learn:daily`, `jobs:search`, `jobs:enrich`, `jobs:match`, `applications:read-forms`, `demos:build`, `repos:suggest`, `memory:leads`), each as a job queue item (below). Every run writes `pipeline_runs`. `POST /api/pipeline/run {task}` queues one by hand.
- Run outcomes: `shared/utils/run-outcome.ts` turns a run's stats into `outcome` (succeeded, partial, failed) and `problems` ("38 failed", "stopped: out of credit"); `pipeline:daily` records its steps' problems. A step the budget stopped reads partial ("stopped: background share of today's AI budget reached, continues tomorrow", or "stopped: daily AI budget reached"; `budgetStop()`), and the daily run's `steps` map records such a step as partial. `GET /api/pipeline/runs` leaves out scheduler heartbeats (`?heartbeats=1` keeps them) and returns `lastDaily` and `lastHeartbeat` on their own.
- Stored errors: never render `status_detail`, `form_error`, `submit_error`, `enrich_error`, or a demo error raw. `plainError()` in `shared/utils/plain-text.ts` gives one plain sentence (no JSON, stack, or internal prefix); `setApplicationStatus()` stores details through it. `cleanFieldLabel()` drops widget text from form labels.
- Review: `GET /api/review/queue`, `GET /api/review/:id`, `POST /api/review/:id/apply` (stage 1), `POST /api/review/:id/approve`, `POST /api/review/:id/reject {reasonCode, reasonText, skills?, skillsMode?}`. A Wrong tech stack reject can name skills (`server/utils/reject-skills.ts`): learning then makes evidence only for them, and skillsMode `lack` writes each one to the knowledge base as a No and answers pending knows/has_done questions about it with No; `avoid` writes nothing. Approve is the only path to `runApproval()` in `server/utils/approval.ts`, which is the only caller of `publishDemo()` and `submitApplication()`.
- Answering on a card (added 2026-11-04): the question leaves every card that shows it the moment it is sent (`answerQuestion()` in `app/composables/useReviewQueue.ts`; the application page does the same). The PATCH refreshes every waiting application before it returns, which takes seconds when many share the question, so a read that started before the save came back never brings it back (`app/composables/review/answered.ts`); the cards that showed it are then read again in one request (`GET /api/review/queue?ids=`). A failed save puts it back. `refreshStoredAnswers()` runs one refresh per application at a time, so two answers saved close together cannot overwrite each other's filled fields.
- Files the app writes (resumes, screenshots, demo repos, sandbox uploads) go under `dataDir()`, next to the database, so they land on the persistent volume.
- Form labels: `matchFact(field, snapshot.fields)` reads a label among its neighbors. A start date inside an education or work history group (Greenhouse's "Start date month" after School and Degree) is not the availability question (`isHistoryDate()` in `server/utils/facts.ts`). `refreshStoredAnswers()` releases a field still waiting on such a misread fact question and skips the question when no field of any application waits on it.
- Browser: `launchBrowser()` / `newBrowserContext()` in `server/utils/browser.ts`. The Docker image installs Chromium at the bundled Playwright version.

## Claude subscription backend (added 2026-11-03)
- Devin's decision: job-hunter is his personal app, so its Claude calls run on his personal Claude subscription (a separate account from his work one) through the official Claude Agent SDK (`@anthropic-ai/claude-agent-sdk`, which runs the bundled Claude Code binary). Never call the Messages API with the subscription token, and never make a request claim to be Claude Code by hand.
- Routing: `stepBackend(purpose)` in `server/utils/ai.ts`. While `NUXT_CLAUDE_CODE_OAUTH_TOKEN` is set every step runs on the subscription (`agent`), bulk ones included; a step `NUXT_AI_STEP_BACKENDS` maps to api uses the Console key, and only while `NUXT_ANTHROPIC_API_KEY` is set. Without the token everything uses the key, as before. `aiToolTurn` (demo builds) always uses the key; production has demos off. `NUXT_AI_STEP_MODELS` still picks the model per step on both backends.
- One call: `runAgentQuery()` in `server/utils/agent-backend.ts` runs one SDK query with the step's system prompt (`systemPrompt` custom), `tools: []`, no MCP servers (`strictMcpConfig`), `settingSources: []`, `permissionMode: 'dontAsk'`, `persistSession: false`, a small `maxTurns`, a throwaway cwd under `dataDir()/agent/work` (deleted after), and `outputFormat` json_schema from the step's zod schema (`agentJsonSchema()`, draft-07, input side). `aiStructured()` validates the answer with the same zod schema, so callers get the same object as from the API backend. Claude Code marks three cache breakpoints itself with a 1 hour lifetime; of `cachedPrompt()`'s breakpoints only the last is sent, also 1 hour, so a request never has more than 4.
- The child process: its environment is an allowlist (PATH, locale, TZ, HOME and CLAUDE_CONFIG_DIR under `dataDir()/agent/home`, the token as `CLAUDE_CODE_OAUTH_TOKEN`, nonessential traffic and the autoupdater off); nothing else of the server's environment reaches it. The token is never in argv, logs, `ai_calls`, errors, or API responses (`redactAgentSecrets()`). In the container it runs as uid 10003 (`claude`, its own user, so demo builds and git cannot read the token). The call returns only after the process has exited (closed, then SIGKILL after 3 seconds). At most `NUXT_AGENT_CONCURRENCY` processes at once per server; a call Devin waits on (not `isBackgroundWork()`) takes the next free slot before background calls.
- Cost: `ai_calls.backend` and `ai_calls.est_cost_usd` (migration 0008, ADD only). A subscription call logs `cost_usd` 0 and the SDK's estimate in `est_cost_usd`, so the daily dollar budget and the background share never stop it (`assertAiBudget()` runs only on the API backend; `aiStopError(purpose)` checks the subscription instead). Settings > Pipeline keeps the stage table to API spend and adds "On your subscription: est. $X today, N calls".
- Limits: a rejected `rate_limit_event` (its `resetsAt`), an assistant `rate_limit` error, or a 429 records the pause in `app_settings` key `subscription_pause` (`server/utils/subscription-pause.ts`; the reset plus 30 seconds, or a backoff of 15 minutes doubling to 2 hours when no reset is reported) and throws `AiSubscriptionLimit` (a subclass of `AiBudgetExceeded`, so callers stop as at the budget). Nothing falls back to the API key. While the pause holds, calls fail fast without starting a process, the worker claims only `NO_AI_TASKS` (heartbeat, the daily parent, search, repos:index, repos:find), and an item the limit stopped goes back in the queue (`pauseItem()`, attempts not counted, note "Paused: ...") to run after the reset; items never fail for it. `pausedByLimit()` decides: the item threw, a per-job item ended `budget`, or its run recorded the subscription stop. A task that caught the limit and finished anyway (the condense fallback) stays done, and approvals are never put back. For a minute after the reset only items Devin started are claimed (background items also wait that minute longer), so chat, drafts, and Apply preparation go first. A run the limit stopped reads partial: "paused: Claude subscription limit reached, resumes at H:MM". The Review health panel and Settings > Pipeline show "Paused: your Claude subscription limit is reached, resumes at H:MM" in amber (`subscription.pause` from `GET /api/pipeline/runs`); the chat and Draft from my records say the same. A rejected token (401, `authentication_failed`) stops subscription calls for ten minutes and shows as an account problem (`aiAccountProblem()` kind `token`) until a subscription call works.
- A model the subscription cannot use is tried once on `NUXT_AI_FALLBACK_MODEL`; any other failure is a plain error, not retried on the key.
- What differs from an API key call (seen in the requests Claude Code sends): Claude Code puts one line of its own before the step's system prompt, and it adds a short environment note (working directory, platform) as a system message. The step's own prompt is otherwise sent unchanged. Thinking matches the API key path: on `claude-opus-5-5`, `claude-sonnet-5-5`, and `claude-haiku-5-5` a request that omits `thinking` (the API key path) runs adaptive thinking, and Claude Code sends adaptive thinking whatever the SDK option says (Opus 5.5 cannot turn it off; Sonnet 5.5 only through `between_tools`, which the SDK does not offer), so effort, passed per step on both backends, is the control. On `claude-haiku-4-5` (the fallback) Claude Code would add a 32K-token thinking budget, so every query passes `thinking` disabled unless `NUXT_AGENT_THINKING` names the step (`agentThinking()`).
- Container: the image copies the SDK's glibc platform binary to `/opt/claude-code/claude` (the Nitro build traces only the SDK's JavaScript) and sets `NUXT_CLAUDE_CODE_PATH`. Measured 2026-11-03: the image grows by 331 MB (binary) plus about 5 MB (SDK JavaScript); each call adds about 0.2 seconds to start the process (0.6 seconds cold); each process holds about 190 MB and idles near 0% CPU while Claude answers.
- Tests: `npm run test:agent` (stubbed SDK: routing, schema validation, budget, the limit and its queue pause, the token kept out of argv, logs, rows, and API views, concurrency; plus one real Claude Code binary call against the local fake API in `scripts/agent-sdk/fake-api.ts`). `scripts/agent-sdk/measure.ts` measures per-call time, memory, and CPU the same way. `scripts/agent-sdk/fake-api-server.ts` runs the fake API for driving a built server: point `NUXT_CLAUDE_CODE_PATH` at a shim that sets `ANTHROPIC_BASE_URL` to it and runs the real binary.

## Job queue (added 2026-11-03)
- Nothing runs in a request or on an in-process timer anymore. Every scheduled run, manual trigger, and background job is a row in `task_queue` (migration `0005_task_queue`, CREATE TABLE only): task, payload, status (queued, running, done, failed, canceled, interrupted), attempts and max attempts, lease owner and expiry, run after, times, the `pipeline_runs` id, the parent (daily run), the last error (through `plainError()`), a note ("Resumed after a restart"), shared progress, and a result. Code: `server/utils/queue.ts` (store, claim, leases, resume, daily chain, views), `server/utils/queue-run.ts` (what each kind of item runs), `server/plugins/queue.ts` (worker loop, schedule, graceful stop), `server/utils/role.ts`.
- Producers call `enqueue()`: the schedule (`pipeline:daily` on `PIPELINE_CRON`, `system:heartbeat` every 15 minutes, both with croner in `server/plugins/queue.ts`; `nitro.scheduledTasks` is gone), `POST /api/pipeline/run`, `POST /api/jobs/search` (waits up to 60 seconds, under Cloudflare's 100 second limit, then answers 202 queued), `POST /api/repos/find` (`repos:find`), new questions (`queueRepoSuggest()`, a `repos:suggest` item 45 seconds out that later questions join), approve (`applications:approve`), Prepare and Prepare again (`applications:prepare-one`), Refill (`applications:refill`), demo rebuild and preview (`demos:rebuild`, `demos:preview`). `?wait=true` on the prepare and refill routes waits on the item. Still inline (they answer the request with a result and start no task): `POST /api/jobs/match`, `POST /api/jobs/:id/rescore`, `POST /api/demos/analyze`, `POST /api/applications/:id/refresh-answers`, `POST /api/pipeline/browser-check`, and the note mapping after a decision.
- Worker: claims the oldest due item with one atomic `UPDATE ... RETURNING` and a 30 second lease, renewed every 10 seconds; runs Nitro tasks with `runTask` unchanged and writes `pipeline_runs` through `withRun()` as before. Lanes: main runs one item at a time (`NUXT_WORKER_CONCURRENCY`); per-job items run four at a time in their own lane (`NUXT_BULK_CONCURRENCY`), so a backlog never holds up an approval, and in that lane a waiting score (`jobs:match-one`, the job read longest ago first) is always taken before a read (`jobs:enrich-one`, which keep their queue order, newest posting first), so the budget ends in scored jobs rather than read ones; the enrich and match steps wait in their own lane; the heartbeat may run beside a long item. Never two of the same task (per-job items excepted), and never two heavy ones (`HEAVY_TASKS`: demo builds and previews, preparations, refills, approvals) at once, across processes.
- Reading and scoring, one item per job, no cap (`server/utils/queue-jobs.ts`): `jobs:search` queues a `jobs:enrich-one` item for every new job; an enrich-one that read its posting queues the job's `jobs:match-one`. The `jobs:enrich` and `jobs:match` steps (full run, or Run in Settings) queue an item for every job still waiting that has none (enrich: prefilter first, best candidates first), wait for all of them, and write one `pipeline_runs` row with the counts (`enriched`, `scored`, `failed`, `pending` = still waiting); per-job items write no run row. Inside a full run the counts cover every per-job item that finished since the full run started, because a job's score runs as soon as it is read, mostly while Read postings still waits on reads. The full run's row carries `enriched`, `scored`, and `pending` too. The daily budget is checked before every Claude call (enrich-one checks `aiStopError()` before fetching anything): a job the budget stops ends `budget`, stays waiting, and the next run after the budget resets queues it again; it is never marked failed for that. `ENRICH_LIMIT` and `MATCH_LIMIT` now cap only the inline `POST /api/jobs/match`. Search and enrich queue their follow-on only where the schedule is on (`autoFollowOn()`), so a worktree spends no Claude credit on its own. Settings and the Review page count per-job items ("Reading postings: 4 now, 37 waiting") instead of listing them; they are pruned after two days.
- Preparing one application: `queuePrepare(applicationId)` in `server/utils/queue.ts` (an `applications:prepare-one` item) is the one call Apply, Prepare from a job page, Prepare again, and the read-forms step (stopped preparations) make.
- Daily run: the `pipeline:daily` item writes its `pipeline_runs` row, queues one child item per step, and frees the worker. A step starts when the one before it ends (failed steps do not stop the chain) and then goes to the front of the queue, so an approve made during a daily run waits for the current step only. After the last step the daily row gets `steps` and `problems` exactly as before. One daily run at a time: queuing another returns the one in flight.
- Resume after a restart: a worker whose process died leaves its lease to run out; the next worker start (or any worker within 30 seconds) puts the item back in the queue with attempts plus one, and the next attempt carries the same `pipeline_runs` row on, marked `resumedAfterRestart` ("succeeded, resumed after a restart" in the run log). After 3 starts it fails. What a rerun does: search dedupes on `source + sourceId`; enrich and match pick rows still pending, so they continue where they stopped; prepare retries rows left in preparing that no queue item holds (`pickRetries`); demos:build builds a demo the restart cut off again first, in a fresh directory (`BUILD_INTERRUPTED`); a rebuild starts its build over.
- Never repeat a submit: an `applications:approve` item cut off mid-run is marked `interrupted`, never retried. `markApprovalInterrupted()` moves the application to `submit_failed` (approve can retry it) with "Interrupted while submitting; check the employer's site before you submit again" when it was submitting, or a "nothing was submitted" sentence when it stopped earlier, and puts a demo left in publishing back to built. Publishing again reuses the GitHub repo that already holds this history and skips a resume card that is already there, so it never makes a second repo or card.
- Graceful stop: on SIGTERM the worker stops claiming, gives the running item up to 25 seconds (Nitro allows 30), then ends its lease so the next start resumes it. `docker-compose.yml` sets `stop_grace_period: 35s`; a platform that kills sooner only means the item waits for its lease to run out (30 seconds) before it resumes.
- Roles (`NUXT_ROLE`, one image): `all` (default; today's single container: web, schedule, worker), `web` (serves the app and enqueues; no schedule, no worker), `worker` (schedule and worker; every path but `/api/health` answers 404). Two processes on one database file work: WAL plus `busy_timeout = 5000`, write transactions for check-then-insert. Live progress the worker shares on its item (`shareProgress()`: demo build turns and lines, the commit search counts) is what a web process shows (`sharedProgress()`); `demoBusy()` and `previewBusy()` read the queue, not memory. `/api/health` returns the role and the queued and running counts.
- Dashboard: `GET /api/pipeline/runs` returns `queue` (running, waiting, daily runs under way, and the last day's interrupted, failed, canceled, and resumed items, plus `backlog`: jobs still waiting to be read and to be scored, counted whether queued or not). Settings > Pipeline shows the backlog in one line ("Waiting: 254 jobs to read, 1,424 to score; resumes when the budget allows.", the last clause only once background work reached its share) and lists the queue with Cancel on waiting items (`POST /api/pipeline/queue/:id/cancel`; a full run under way loses its waiting steps; approvals and preparations are not cancelable); the Review page health panel shows the running item and what waits, or an interrupted approval. Text comes from `shared/utils/queue-text.ts` ("Waiting: Score matches, queued 2 minutes ago").
- Deploys: a push to main still restarts the container, which pauses the queue until it is back. Nothing is lost and no run needs to be held for: the item that was running resumes from where its task left off, and waiting items keep their place. One exception: if Settings > Pipeline shows "Running: Submit an approved application", wait for it, because a restart ends that one interrupted and Devin then has to check the employer's site before approving again.

## Decide first (added 2026-11-03)
- Scoring plans the gaps: one Claude call per job, purpose `match_gaps` (`MATCH_GAPS_PURPOSE` in `server/utils/scoring.ts`; map it in `NUXT_AI_STEP_MODELS`), judges every requirement (have, reframe, partial, lack, unknown, each citing a knowledge base key) and scores stack, seniority, and domain. `applyJudgments()` in `server/utils/skills-judge.ts` turns that into the final statuses (written back to `requirements_json`; a reframe is `have` with `reframed` and a `note`), the must-have share (0 to 45, from the statuses, over must-haves that are not profile facts or soft skills, the same set the card counts), and the gap plan (`ScoreBreakdown.skills.gap`, kept by code rescores). Code enforces: a status without a real entry is unknown; Devin's answers win; years against profile/Years of Experience are arithmetic; years, education, certifications, and what the call marks `inGapPlan: false` stay out of the plan. Scoring creates no question: an ask points at an existing question (exact or `sameSubject()`), and `askGapQuestions()` asks the rest when the job gets a Decide card (never for sandbox jobs, never twice for the same requirement on a rescore). `analyzeGaps()` (gap_candidates, gap_decisions) now runs only for a job scored before this.
- Two stages. Stage 1 (Decide, status `to_decide`): for every job scoring at or above 70 (`DECIDE_THRESHOLD`), `applications:read-forms` (the daily step where `applications:prepare` used to be, at most 12 forms a run) creates the application row, copies the scored gap plan onto it (or runs `analyzeGaps` for an older score), and reads the employer form in Chromium without filling it (`readForDecision()` in `server/utils/apply/decide.ts`). `deriveAnswers(..., { mode: 'decide' })` fills personal facts, maps options (`form_option_map`), and asks a question for each fact the form needs; every field that needs Claude's judgment is marked `atApply` and nothing is written for it.
